# 主协调者的只读代码交叉核对

以下在独立测试员提交发现后由主协调者检查，未提供给其他测试员，也没有修改被测代码。它用于解释已有证据和提出修复边界，不代替黑盒复现。

| 已观察的问题 | 代码交叉核对 | 可实施的改进方向 |
| --- | --- | --- |
| 英文否定房型被反向当成需求（PRO-01） | 直接抽取当前源码的纯函数复现：`_extract_room_type` 对 T1 的 `not a room or studio` 返回 `studio`，对 T19 的 `remove the rooms in shared houses` 返回 `shared`。它按同义词子串命中，没有否定作用域 | 对排除、询问、假设和实际偏好更新分别建模；整租应有可表达的明确类型，不能依赖 Any/空值来排除合租 |
| 引用房源租金盖过明确预算（PRO-03） | `_extract_budget` 优先取第一处货币数字。对 T19 原文，纯函数直接返回 1495/月，尽管同句明确要求保留 1800 月上限 | 先判断数值角色及更新意图，再解析实际预算；保留预算陈述的来源、时间与覆盖关系，房源报价不自动成为预算 |
| 比较后 `search_criteria={}` 清空面板（STU-05） | `app/unified-ui.html` 的消息处理用 `if (data.search_criteria) applyCriteria(...)`；JavaScript 空对象为真。`app/core/langgraph_agent.py::_criteria_for_frontend` 的注释也说明空对象会清表单，但仍有实际比较路径返回空对象 | 明确区分不更新、完整快照与显式清空；让所有回答路径共享同一条件契约，并以浏览器条件面板做回归断言 |
| 保存偏好吞掉同轮复述/摘要（STU-08） | `app/core/agent_loop.py` 最终格式化以“是否执行了 remember 之外的工具”决定 `preserve_content`。`app/core/memory_contract.py` 在 false 时直接返回保存通知；纯文字复述并不需要其他工具 | 以用户要求的独立任务决定保留内容，保留确定性的保存结果通知，同时完成复述/摘要，不以工具数量推断是否存在多任务 |
| 关闭重开后语言回到英文（STU-10） | `app/unified-ui.html::initApp` 固定执行 `setLanguage('en')`；`setLanguage` 只更新当前变量和 DOM，没有恢复已保存选择的逻辑 | 将界面语言作为可持久化偏好，初始化时恢复；与聊天回答语言分别定义 |
| 卡片没有呈现已存在的过期/未知/排除状态（STU-12） | 前端没有直接消费 `possibly_outdated` / `candidate_status` 字段的路径；黑盒证据已经展示返回元数据与卡片标签的差异 | 用共享卡片展示契约呈现来源、新鲜度、整体资格状态、未知项与排除理由；收藏重访时区分“保存当时的状态”和“现在仍满足需求” |
| 房源编号触发两千万预算解释（STU-02） | `app/core/tools/search_properties.py::_extract_budget` 的主数值匹配限 3–5 位、有效值上限 20,000；不能仅凭错误回复断言该正则把 8 位编号写成预算 | 暂按可证实的响应错误处理；继续追踪模型抽取、冲突解释与状态组装。为 URL/房源 ID、价格、预算、日期分别提供类型与来源，不把所有裸数字当约束 |
| 正文房源 URL 与同响应卡片 URL 不同（STU-03） | 原始浏览器响应可直接核实，见 parent_validation.json；没有访问外部链接，也未确定是哪段模型或格式化逻辑造成 | 房源身份和链接从结构化实体确定性渲染；对正文中的房源引用验证其属于本轮/引用上下文的已知实体，不能只校验主机名或价格 |

取消条件仍残留、异常未来日期、单次记忆保存失败等的精确根因尚未确定。特别是，意外日期不能据此定性为跨用户泄漏，保存失败也不能据此认定数据库损坏。新的独立身份与登录恢复已有通过样本。

纯函数复现只抽取列出的函数和常量，不导入整个产品，不执行网络或模型请求，也没有修改代码。输入与结果保存在 [deterministic_reproductions.json](deterministic_reproductions.json)。

下一轮回归应围绕可观察行为建立：显式取消得到 null；比较不清空条件；不相关编号不改变预算；正文与卡片实体一致；保存结果与同轮答复都完整；手机账号入口可正常操作。普通接口成功率和已有单元测试通过数不足以替代这些断言。

## 授权API补测后的身份核对

`app/app.py::_enforce_auth` 以session的authenticated标志放行；`_current_auth` 和 `_authed_user_id` 只检查该标志与user_id格式，没有核对账号仍存在或会话已撤销。`resolve_identity` 随后将此身份作为权威身份。`forget_me` 虽实际删除账号记录并清理调用方Cookie，也没有使其他已签发的Cookie失效。

公开API创建的C已删除账号行，旧Cookie仍能创建新会话且重启后可访问，见 [API补测](cross_identity/REPORT.md)。这将问题定位到认证生命周期校验，不能解释为Cookie签名可伪造；篡改签名的测试返回401。普通退出仅移除当前session字段，也缺少服务端撤销副本的机制，作为单独设计项记录。

建议把账号有效性、会话版本/sid撤销合成为统一的服务端身份校验，并让auth/me、Flask API和原生聊天入口共享；删号失效回归应包括旧Cookie与真实重启。完整验收顺序见 [修改意见](RECOMMENDATIONS.md)。
